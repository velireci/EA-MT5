### What the code does today (read from src/include/ExitReconciliation.mqh, not run)
In `ER_Reconcile` a snapshot with `position_found == false` always goes to `ER_Block(... "POSITION_MISSING ...")` BEFORE the executions are even summed: `status` becomes BLOCKED, `reason` is overwritten; `confirmations`, `executed_steps`, `request_id` are untouched (consistent with the relayed confirmations 1). Consequences: (1) a record that was DONE is rewritten as BLOCKED (generation 5), so the stored status no longer says DONE; (2) BLOCKED is terminal (`ALREADY_BLOCKED` is the first test), so this record can never return to DONE and no code revives it; (3) a position that was finished and proven by history is treated like an unexplained absence. The behaviour is safe (no request, no retry, nothing deleted) but it is the wrong answer for a finished position.
The adapter has the data to tell the cases apart and does not expose it: for `n_pos == 0` it still builds the snapshot (`found=false`, volume 0, the linked exit deals, `complete` from the six proofs), and every deal carries entry type, volume and position id. It does not total the opening volume against ALL exit volume, and it does not separate INOUT deals from other non-exit entries (both counted in `excluded_entries`).
### Three states to keep apart
* FINISHED, PROVEN BY HISTORY: position not open; history readable, not truncated, stable; the opening (IN) deal present; no INOUT deal; the deduplicated sum of ALL exit (OUT) deal volumes of this position identifier equals the opening volume on the volume grid; and the six existing completeness proofs hold for the mapped request.
* ABSENT, UNPROVEN: position not open but any of that missing -> today's BLOCK stays.
* NOT FINISHED: position open -> unchanged.
