## 4. Live mode (InpAsOfTime = 0)
Attach to an XAUUSD H4 chart. The logic is replayed when an H4 bar CLOSES; the forming bar is never read and no price is used. At start, restart, input change or recovery from a data problem the current history is the BASELINE: its events are drawn dimmed/coloured by type and are NOT reported as new. Events produced by bars that close after the baseline are drawn larger, in green, prefixed `>> NEW`, listed `[NEW]` in the panel and logged as `T003 NEW EVENT`. If the evaluation is not reliable, or the previous bar's state cannot be reproduced, nothing is reported as new and the log says why (`T003 consumer ...`). Bias, replay-window T002 structure, phase and setup changes seen while running are logged (`BIAS CHANGED`, `REPLAY-WINDOW T002 structure CHANGED`, `PHASE CHANGED`, `SETUP CHANGED`) and the last four are shown in the panel (details view). A clear or a recovery from a data problem starts a NEW baseline: the values labelled 'since baseline' (the NEW market event count and the observed changes) are set to zero, nothing in the history is reported as NEW, and the totals of the session are written to the Experts log only (`T003 SESSION LOG (Experts only) ...`, also at removal). Only MARKET events are reported as `NEW`; observations (CONTINUATION, INTERNAL_BREAK, NONE_WICK, CONFLICT, the diagnostic SNAPSHOT_CROSSED) are logged as `T003 observation (not a market event)`. MODEL DISAGREEMENT (section 6.2) is logged once per change.
When the H4 series is not ready or a copy fails, all `velo_t003_` map objects are removed and the panel states the reason; when the data returns, the picture is rebuilt from a new baseline.

## 5. Historical mode (InpAsOfTime > 0)
Set InpAsOfTime in SERVER time (the time axis of the MT5 chart). Only bars closed by that time are used, no live price is read, new bars do not change the picture, and no event is marked NEW (the panel lists the latest events with their bar times). The panel shows the as-of time and the last closed H4 bar used. To compare with a client example pick an as-of time just before the event, then a few bars later, and record what changes. A changed input re-initialises the EA.

## 6. Reading the picture
Everything is a PROPOSAL / PROTOTYPE. When the support flag is LIMITED_BY_HISTORY NOTHING proposal-derived is drawn (no structure, no setup, no liquidity layer, no disagreement) and no market event is raised: only the reliability part of the panel remains (6.6).

### 6.0 The compact panel (default) and how it fits the chart
- Lines of the compact view, in this order (each has a priority, 0 = essential): the title (PROPOSAL, no trading); mode and date (LIVE, or HISTORICAL with the as-of time in server time); the symbol and the last closed H4 bar; `T003 bias (PROTOTYPE proposal, not the client's direction): BULL|BEAR|NONE`; `T002 baseline (lookback N): <dir> (<HH+HL|LH+LL|...>)`; the MODEL DISAGREEMENT text when it exists (otherwise a short `none` line); `current level <price> (solid) | snapshot <price> (dashed, reference only)`; `phase <phase> | READY yes/no`; `FVG: <id> <FRESH|TOUCHED|INVALID> [low - high]` (the reconfirmation FVG when there is one, otherwise the latest eligible FVG; PROPOSAL); `reliability: CONVERGED|SEEDED|LIMITED_BY_HISTORY <R used>/<B depth> - reason`. Less important lines (the definition of the disagreement, the note that the replay-window structure DIFFERS from the baseline, warnings, the export path, a hint) have higher priority numbers.
- The panel is wrapped to the chart width and its height is limited to the chart height: when the lines do not fit, the LOWEST priority lines are dropped (the last ones of a priority first) and a final line says how many are hidden; the font is NOT reduced (InpPanelFontSize, minimum 7). On a chart resize (`CHARTEVENT_CHART_CHANGE`) the same lines are laid out again for the new size (nothing is re-evaluated and no map object is touched; nothing happens while the size is unchanged). The line budget, the wrapping and the size functions are pure helpers (`H3LPanelBudget`, `H3LWrap`, `H3LPanelRows`, `H3LPanelCols`) tested in `T003_LayersTest.mq5`; the layout on a real chart is UNVERIFIED.
- `InpShowDetails = true` adds the long view (priority 3 and up): depths, the replay-window structure with its since/previous, the T002 source swings, the phase reason, the last bias event, the observed changes since the baseline, ids and known times of the levels, the SETUP block, the events, the liquidity list. Everything in the long view is also written to the Experts log once per evaluation (`T003 SUMMARY`, `T003 DETAIL structure / T002 sources / level / setup / reconfirmation FVG / historical liquidity`).

### 6.1 T002 baseline and the replay-window structure (the market structure as T002 reads it, a proposal)
- The T002 EA analyses the last `InpLookbackBars` (L, default 300) closed H4 bars. The T003 replay window is longer (e.g. 2000 bars). The compact panel therefore shows the T002 BASELINE, computed independently with the same inputs and functions as the T002 EA (the last L closed bars, 2/2 swings, `H4DeriveDirection`; if fewer than L bars exist, all of them, and the panel says so): `T002 baseline (lookback 300): BEARISH (LH+LL)`.
- The direction derived from the whole replay window is a DIFFERENT value and is called `replay-window structure` (long view and Experts log). When it differs from the baseline the panel says `replay-window structure X DIFFERS from the T002 baseline Y (the replay window is longer than the lookback)`. The replay itself (the T003 seed and logic) still uses the replay-window value; this round did not change the logic.
- Panel (long view): `replay-window structure (whole window, 2/2 swings): ...`, since which bar, the previous direction, and `T002 sources (replay window)`: the two latest confirmed swing highs (`H-latest`, `H-prev`) and lows (`L-latest`, `L-prev`), each with price, PIVOT time and CONFIRMATION time (`known`).
- Chart: `T002 baseline(N): <dir>` above the last closed bar (tooltip: the full statement and the replay-window value). The four source marks `T2 <tag> <price>` (white, the tooltip holds pivot and confirmation times) are drawn only with `InpShowDetails = true` (technical proposal: they sat on the same swings as the level pivots and overlapped). The words HH+HL / LH+LL are the client's description of direction (N1); WHICH swings count is NOT confirmed (the 2/2 fractal is a proposal).

### 6.2 T003 prototype bias, the protecting level, MODEL DISAGREEMENT
- `T003 bias (PROTOTYPE proposal, not the client's direction): BULL|BEAR since ...` (compact) and, in the long view, the phase reason; the bias is also written under the last closed bar (`T003 proto BEAR SWEEP_WAIT`, tooltip: the full statement).
- CURRENT protecting level: a SOLID line from its pivot to the right edge, short label `CURRENT <price>` (tooltip: `CURRENT protecting level (PROPOSAL, solid) <price> known <time> - decides FLIP`). It follows the revision 10 ratchet, so it can move. The swings it was selected from are marked `S`, `LL`/`HH`, `prevLL`/`prevHH` with the price (tooltip: pivot and confirmation times).
- MODEL DISAGREEMENT (technical definition, a PROPOSAL, stated in terms of the T002 BASELINE of section 6.1): it exists ONLY when the T002 baseline is BULLISH (HH+HL) and the T003 bias is BEAR, or the T002 baseline is BEARISH (LH+LL) and the T003 bias is BULL. A baseline MIXED or UNKNOWN, or no T003 bias, is NOT a disagreement. The direction of the whole replay window is NOT used for it (the long view shows whether the same test with the replay-window structure would give another result). When it exists the panel line and an orange label next to the last closed bar read `MODEL DISAGREEMENT - client validation pending: T002 baseline (lookback N) <dir> (<HH+HL|LH+LL>) vs T003 prototype bias <BULL|BEAR>, since closed bar <open time> (known <close time>), <n> closed bar(s)` (the chart label is the short `MODEL DISAGREEMENT: baseline <dir> vs T003 <bias>, <n> bars`, the tooltip the full text); a dotted vertical line marks the start. The start and the count are derived from the replay by ABSOLUTE bar times: at each earlier bar the baseline is the T002 direction of the L closed bars ending there, against the bias after that bar's close; a run that reaches the start of the trusted bars says `or earlier`. It is logged ONCE per change (`T003 MODEL DISAGREEMENT ...`); at start, rebuild, gap and in historical mode it is labelled a STATE, not a market change. It is a finding about the proposal (the bias holds until a close beyond the protecting level, tasks section 13.6), not an error.

### 6.3 SETUP (separate from the structure)
- Compact panel: `phase <phase> | READY yes/no`, the snapshot next to the current level, and the FVG line. Long view, block `SETUP`: `setup_id`, direction, type (WICK or SWEEP), reason (STRUCT or INTERNAL), phase (ACTIVE = no setup, HOLD, SWEEP_WAIT, RECONFIRMED), `READY yes/no` (true only in RECONFIRMED; M15 is not built, so READY is not an entry), the SNAPSHOT level, the current level, the wick record (`source_wick_time | known | detected_at | retroactive`), the internal sweep, the number of eligible new FVGs and the reconfirmation FVG with its bounds, confirmation time and valid-from. PRE_WICK FVGs (older than the wick) are listed as ineligible. The two entry-block flags are REPORTED ONLY.
- Chart: the SNAPSHOT of the protecting level at the creation of the setup is a DASHED goldenrod line labelled `SNAPSHOT <price> (ref)` (`=CURRENT` when it is the same level; tooltip: known time); the CURRENT level is the SOLID line (6.2). The snapshot never decides a flip. Short `WICK`, `det` and `SWEEP` marks (tooltips: the timestamps), eligible FVG rectangles (labelled `FVG bull|bear FRESH|TOUCHED|INVALID`, gold and `FVG ... RECONF` for the reconfirmation FVG; tooltip: id and bounds), `SETUP <phase> ready ...` under the last bar (tooltip: setup_id, type, reason). SETUP_ENDED events (reasons INVALIDATED_BY_FLIP, REPLACED) appear as event texts; SNAPSHOT_CROSSED is a diagnostic and appears only with InpShowNonMarket.

### 6.4 HISTORICAL LIQUIDITY layer (PROPOSAL - historical liquidity, not ERL / target / protecting level)
- What: the confirmed 2/2 swing highs and lows (the T002 swing function, confirmation time known at the evaluation) that NO later closed bar has exceeded by a WICK: a later `high` above a swing high, or a later `low` below a swing low (strictly; an equal value is a touch). Closed bars only, no live price. Drawn as thin DOTTED lines from the pivot time to the right edge with a small label `liq <price>` at the pivot (tooltip: kind, pivot and confirmation times; a swing that already carries a level-pivot mark keeps its line but no second text); the long view lists them (`liq SH|SL price pivot ... known ...`).
- Limit: at most `InpLiqMax` (default 6), chosen as the levels NEAREST to the close of the last closed bar (ties: the more recent pivot). The panel says how many unexceeded swings exist in total. `InpShowLiquidity = false` switches the layer off.
- It does NOT change the bias, is NOT an ERL, a target or a protecting level, and is not fed to `H4Bias.mqh` (it lives in the drawer and `H4BiasLayers.mqh`; static checks forbid any write into the state). The client confirmed the CONCEPT of historical liquidity (N2); the 2/2 fractal and this mechanical definition are PROPOSALS, as is the choice of the nearest levels. An old liquidity level is not a reason to keep a direction (N2).

### 6.4b INTERNAL LIQUIDITY (revision 14 PROPOSAL / PROTOTYPE, awaiting the client; NOT the historical liquidity layer of 6.4)
- What: the logic (`H4Bias.mqh`) now keeps, per bar, the SET of unconsumed internal levels: confirmed swings of the side opposite to the bias, pivot later than the pivot of the CURRENT protecting level, price strictly inside it, not crossed (adverse extreme strictly beyond) by any closed bar since their confirmation. A crossing is raised per level as INTERNAL_BREAK (close beyond) or INTERNAL_SWEEP (extreme beyond, close not beyond); a sweep creates a SWEEP setup only from ACTIVE or SWEEP_WAIT (`setup=1`), in HOLD / RECONFIRMED the sweep is only an event (`setup=0`). It never decides FLIP and never moves the protecting level. Rules: tasks/T003-h4-bias-change.md section 16.
- Display: the compact view is unchanged. The long view has one line `internal liquidity (revision 14 proposal ...): N unconsumed level(s), most adverse IH<pivot time> <price>`; the chart shows only the most adverse level of the set as a thin dotted line with the label `int.liq <price> (N)` (the other levels of the set are not drawn). The label of an event is unchanged (`SWEEP bear`); several INTERNAL_* events in one bar get separate slots and separate tooltips (each carries its own level id). The A/B reason `AB_STRUCTURE_DIFF` now also covers a different set of unconsumed internal levels.
- Event detail (tooltip, Experts log): `INTERNAL_SWEEP ... dir=..;lint=<level id>;sweep=<bar>;restart=0|1;setup=0|1;top=0|1` (a superset of the earlier detail: `restart=` is kept); the level id is `IH`/`IL` + the pivot time.
- Not drawn / not changed: the 2/2 historical liquidity layer (6.4) is separate and still read-only; the EA still sends no order. Not compiled in MetaEditor and not observed in MT5.

### 6.5 Events
`NEW` markers, the last events and the counts as in section 4. Event texts above the bar are SHORT (`FLIP bear`, `SET bull`, `WICK bear`, `SWEEP bull`, `RECONF`, `END`, ...; `NEW` in front and green for a new event); the full event id, direction and detail are in the tooltip and in the Experts log.

### 6.6 A/B reliability
Compact: `reliability: CONVERGED 2000/1700 (R used / B depth) - reason`. Long view: `depths: R requested/used, B depth, warm-up, check depth, bars available` and the note. Reasons when LIMITED: `AB_STRUCTURE_DIFF` (replays A and B differ in the structure), `AB_SETUP_DIFF` (in the setup), `AB_EVENT_DIFF` (in the events of the compared zone), `ANCHOR_IN_WARMUP`, `ANCHOR_HISTORY_MISSING`. `ORG_DIFF A=.. B=..` in the note is INFORMATIONAL (the origin name differs; never a reason). When LIMITED the bias is UNKNOWN, the DIAG lines (section 9) explain why, and nothing else is drawn. SEEDED = a reliable state whose origin is the T002 seed. CONVERGED = A and B agree.

### 6.7 Objects
Only objects whose name starts with `velo_t003_` are created or deleted (the panel uses `velo_t003_pnl_`). Manual objects and the T001/T002 objects are never touched. Object names use times and a short hash of long ids (chart object names are limited in length; MT5's limit is believed to be 63 characters, NOT verified here). Running T002 and T003 on the same chart is possible but their panels may overlap; use the corner inputs.

### 6.8 Chart labels: short text, tooltip, stable position
- Every dynamic label has a SHORT text; the full text is the object tooltip (hover over the label in MT5) and the Experts log. The three things to tell apart: `CURRENT <price>` on the solid protecting-level line (above the line), `SNAPSHOT <price> (ref)` on the dashed line (below it), and `FVG ...` on the rectangles.
- The vertical position of an event label is a function of the bar time (one of three lanes) and of the label's rank among the events of the SAME bar in the logic's own event order (`H3LLabelSlot`): the same event always gets the same position, independent of the draw order, of how many events are drawn and of any random value, so a redraw never shuffles labels. Only the position of the TEXT is offset; the event bar, every level line and every FVG bound keep their real coordinates (a static check asserts that the price arguments of the level lines and the FVG rectangles are the real values). Labels can still touch when many events lie on neighbouring bars: reduce `InpMaxEvents`, or hover for the tooltip.

## 8. Reading a change notice
`BIAS CHANGED`, `REPLAY-WINDOW T002 structure CHANGED` (named `T002 DIRECTION CHANGED` before version 1.11; it is the whole-window value, not the T002 baseline), `PHASE CHANGED` and `SETUP CHANGED` (panel "observed live" and Experts log) appear ONLY when the new closed bar followed the previous evaluated bar directly and the previous state was reproduced by the new window (consumer status OK, the same step that makes an event NEW). If bars were missed (consumer GAP), the window slid or the depth changed (REDERIVED) or the same bar was evaluated twice, a difference is logged as `T003 RE-DERIVATION (consumer ...)` with the cause and is NOT a market change. Before the diagnostics round every difference between two reliable evaluations was shown as a change (reporting defect, fixed; reports/T003-verification.md section 10.3).

## 9. Diagnostics and candle export (LIMITED_BY_HISTORY)
Why: the owner's observation (relayed) was LIMITED_BY_HISTORY with `AB_STATE_DIFF+AB_EVENT_DIFF+ANCHOR_IN_WARMUP` at R=1000 live and at 1000 and 2000 bars as of 2026.10.06 00:00. The panel and the log now say WHY, and the exact candles can be written to a file and replayed offline in the Python model.

Experts log, once per last closed bar and reason (`T003 DIAG1` .. `T003 DIAG8`; all times are server times as YYYYMMDDHHMM):
- DIAG1 verdict and reasons, the whole series, the A window (start, bars, warm-up end), the B window (start, bars, warm-up end) and the comparison-zone start (= B's warm-up end, events dated from there are compared);
- DIAG2 / DIAG3 the final state of A and of B: direction/phase, origin (BREAK or SEED) with its reference time and the bias start, the protecting level (id, price, known time, the three pivot times), the anchor and WHICH reference binds it (`origin`, `lv_pivot`, `lv_ext`, `lv_prev`, `wick`, `sweep`);
- DIAG4 the FIRST differing field in the explicit order `BIAS>LV>EX>LI>BS>SU>PH>SRC>WAIT>REC>RSN>EL` (the first five are the STRUCTURE key, the rest the SETUP key) with both values (for EL also the first differing FVG track); an `ORG_DIFF` is shown as provenance only;
- DIAG5 the first differing EVENT in the zone (index, type, absolute time, id, both sides) or `count differs: nA vs nB` with the first extra event;
- DIAG6 / DIAG7 for A and B: whether the protecting level is UNDEFINED at the last bar, since which bar, how many bars, what began the run (FLIP, BREAK_SET, SEED, LEVEL_DROPPED), runs and bars without a level in the window, flips in the window and after the run began, and WHY there is no level (no candidate / candidate already closed beyond, with the bar);
- DIAG8 on how many of the common bars the A and B state keys differ, first and last such bar.
The causes named by these lines are what the two replays show; why the situation arises on a real series is a HYPOTHESIS until a real CSV is replayed.

CSV export (`InpExportCandles = true`): after each evaluation the EA writes the full closed-bar set it evaluated (replays A and B are subsets of it) to
`<terminal data folder>\MQL5\Files\velo_t003_diag_<symbol>_<open time of the last closed bar, YYYYMMDDHHMM>.csv`
(File > Open Data Folder, then MQL5\Files; the Experts log prints the full path as `T003 EXPORT: ...`). The file NAME follows the symbol and the last bar; the CONTENT is the latest analysed set. The EA remembers a set key = symbol, as-of, last bar time, first bar time, number of bars and an order-sensitive 64-bit FNV-1a hash of every bar's time and open/high/low/close rounded to the symbol's digits. When ANY part of the key changes the file is written again under the same name (the existing file is OVERWRITTEN, never versioned): so history that is added or corrected while the last candle stays the same (a partial history that grows, a data fix) gives a new file content. A change below the exported precision, or in volume/spread, does not rewrite it. The `T003 EXPORT` log line prints the key. In live mode a new file appears for each new H4 bar, so turn the input off after collecting what you need. The file holds `#` header lines (symbol, period, digits, live/historical mode, the AsOfTime input, first and last bar, left/right, lookback, rebuild input, r_req, r_eff, b_depth, check depth, warm-up, hard cap, the EA's own result flag and reason, note) and then the columns `time_epoch,time_server,open,high,low,close,tick_volume,spread,real_volume`. Only closed bars are written (the forming bar is never read). Nothing else is written and no trading function is involved.

Offline replay (Python 3, no MT5 needed): `python3 tests/t003_replay_csv.py <file.csv>` runs the Python model on the file with the header's parameters, prints the same DIAG lines and says `REPRODUCED` when the model's flag and reason equal the EA's (header). `NOT REPRODUCED` means the model and the MQL5 code disagree on this series: that is itself the finding. Options: `--rebuild`, `--lookback`, `--asof "YYYY.MM.DD HH:MM"` for offline experiments (no reproduction claim is made then). A file whose header says `source=SYNTHETIC` is test data, not market data.

## 10. Known limits
- The diagnostics and the export are UNVERIFIED in MT5 (not compiled). Their text is checked only against the Python model.
- The panel size is estimated from the font size (character width is approximated). Since 1.11 it is laid out from the chart width and height, drops the lowest priority lines when the chart is too small and is laid out again on a chart resize; the real MT5 character width of the Consolas font is NOT measured, so the fit on a real chart is UNVERIFIED (a large font on a very small chart can still lose lines, which the final `... N more line(s) hidden` line reports).
- Tauro versus TradingView candle and time alignment is not verified.
- A restart loses the in-memory NEW markers and the list of observed changes; the history is always rebuilt from the bars. A clear / recovery within a run zeroes the since-baseline values (section 4); the session totals exist only in the Experts log.
- The T002 baseline needs L closed bars at each examined bar: for bars very early in the replay window it uses all bars before them (the panel marks a baseline with fewer bars than the lookback). The disagreement run is computed from the trusted region (bar index L of the window) on, where every baseline has its full L bars.
- The integration of the revision 10 prototype, MODEL DISAGREEMENT, the SETUP block and the liquidity layer are UNVERIFIED in MetaEditor and on a chart. The pure helpers were run only in a C++ transliteration (tools/t003-xlate-check.sh).
- The liquidity layer, its nearest-first choice, the disagreement definition and the fractal 2/2 swings are technical proposals. The client confirmed the concept of historical liquidity and the wording HH+HL / LH+LL, not these algorithms.
- Chart object names are short (hash of long ids) because MT5 limits their length (believed 63 characters; not verified). The previous drawer built names from full event ids; they could have exceeded that limit, which was never observed because the only observed run was LIMITED_BY_HISTORY (nothing drawn).
