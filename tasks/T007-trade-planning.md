## 1. Trade plan - `TP_BuildPlan` / `build_plan`
Inputs (all chosen OUTSIDE): signal_id, setup_id (non-empty, non-blank strings), direction, E_raw, S_raw, optional T_raw, risk budget (monetary; the base of the 1% is not chosen), tick_value, symbol params (tick_size, digits, point, stops_level, optional bid/ask) and volume params (min, step, max, cap_lots). It only CALLS `TG_Compute` and then `PS_Compute` with the geometry result as the sizing input; no formula or normalization is copied (static check: no MathFloor/Ceil/Round/NormalizeDouble in the module).
- Statuses (first failure wins): `INVALID_INPUT` (stage INPUT; tags `INVALID_SIGNAL_ID`, then `INVALID_SETUP_ID`; before any geometry), `GEOMETRY_REFUSED` (stage GEOMETRY; `under_status`/`under_reason` = the T005 status and reason, e.g. SL_WRONG_SIDE, ZERO_RISK, INVALID_DIRECTION, INVALID_INPUT with INCOMPATIBLE_TICK_DIGITS or non-positive price, TARGET_WRONG_SIDE, BELOW_STOPS_LEVEL, PENDING_TOO_CLOSE), `SIZING_REFUSED` (stage SIZING; the T006 status and reason incl. SKIP_BELOW_MIN_VOLUME, SKIP_ABOVE_MAX_VOLUME, SKIP_ABOVE_CAP and the INVALID_INPUT tags), `OK` (stage COMPLETE). Sizing is not called after a geometry refusal.
- OK plan: e_out, s_out, tp, level_2r, partial_price (`PARTIAL_AT_2R`, client answer 80% of the initial volume, NO volume split here), r_geom, volume_out, risk_model (= T006 risk_realized, labelled `LINEAR_MODEL, COSTS_NOT_MODELLED`), tp_equals_2r (passed through; the remainder behaviour is still open) and the constant label `PLAN_ONLY / NOT_AN_ORDER`.
- Any refusal: every numeric field is 0 and the reason names the stage; ids and direction are echoed.

## 2. Permit checks - `TP_CheckPermit` (pure) / `TP_Authorize` (check + registration)
Inputs: the plan (must be OK), a caller SNAPSHOT (data state READY/NOT_READY/UNKNOWN + reliability flag, session OPEN/CLOSED/UNKNOWN, news CLEAR/BLOCKED/UNKNOWN, spread CLEAR/BLOCKED/UNKNOWN, open_positions, trades_today, existing_risk), the LIMITS (max_positions, max_trades_per_day, combined_risk_cap; each a value or UNSET) and a caller-owned registry (string array whose size is the capacity, plus a count). No clock, no feed, no definition of win/loss.
Output: ALLOW/BLOCK, primary reason (first), all reasons in this FIXED order (one tag at most per group):
1. plan: `PLAN_NOT_OK` | `PLAN_INVALID_ID` | `PLAN_INVALID_VALUES` 2. data: `DATA_UNRELIABLE` (READY with flag false) | `DATA_NOT_READY` | `DATA_UNKNOWN` 3. session: `SESSION_CLOSED` | `SESSION_UNKNOWN` 4. news: `NEWS_BLOCK` | `NEWS_UNKNOWN` 5. spread: `SPREAD_BLOCK` | `SPREAD_UNKNOWN` 6. registry: `REGISTRY_INVALID` | `DUPLICATE_SIGNAL` | `REGISTRY_FULL` 7. positions: `POLICY_UNSET:max_positions` | `INVALID_SNAPSHOT:max_positions` | `INVALID_SNAPSHOT:open_positions` | `MAX_POSITIONS_REACHED` 8. trades: `POLICY_UNSET:max_trades_per_day` | `INVALID_SNAPSHOT:max_trades_per_day` | `INVALID_SNAPSHOT:trades_today` | `MAX_TRADES_REACHED` 9. risk: `POLICY_UNSET:combined_risk_cap` | `INVALID_SNAPSHOT:combined_risk_cap` | `INVALID_SNAPSHOT:existing_risk` | `COMBINED_RISK_EXCEEDED`.
A state outside the documented values gives `INVALID_SNAPSHOT:<state field>`. Everything uncertain blocks (fail closed). An UNSET limit ALWAYS gives `POLICY_UNSET:<name>`: the module never invents 2-vs-3 trades, win counting, pending-order risk reservation or manual-trade handling.
Boundary conventions (PROPOSALS for review, not client answers): `open_positions < max_positions` allows, `==` blocks; `trades_today < max_trades_per_day` allows, `==` blocks; `existing_risk + plan.risk_model <= combined_risk_cap` allows (exactly at the cap is allowed; tolerance only binary noise, `TP_RISK_ULPS` = 4 ulps of max(1, cap), so one cent over blocks). The risk comparison is skipped when the plan is not valid. Overflow-free form (existing >= 0, risk > 0, cap >= 0, all finite; `tol = TP_RISK_ULPS * DBL_EPSILON * max(1, cap)`): `remaining = cap - existing`; if `remaining >= 0` exceeded iff `risk - remaining > tol`, else `over = -remaining` and exceeded iff `!(over <= tol && risk <= tol - over)`; the sum and `cap + tol` are never formed; a non-finite intermediate counts as exceeded (`COMBINED_RISK_EXCEEDED`, no separate overflow tag). Same expression and constants in MQL5 and Python. The test table uses arbitrary values (3, 5, 5000.0), not client limits.
ALLOW is a permit result only, never an executed order.
Duplicate protection: `TP_Authorize` records plan.signal_id in the supplied registry ONLY on ALLOW; a BLOCK never consumes the id. The registry is a pure in-memory caller-owned structure: NOT atomic, NOT persistent, no broker/restart recovery. Overflow: a new id at capacity gives BLOCK `REGISTRY_FULL` (never dropped or overwritten silently); capacity 0 behaves the same; a count outside 0..capacity gives `REGISTRY_INVALID`. A duplicate is checked before capacity. The capacity check is independent of the id; `TP_Authorize` writes only when the decision is ALLOW and `0 <= count < capacity` (a final defensive guard gives BLOCK `REGISTRY_FULL` without writing); every refusal leaves ids and count unchanged.

Plan validation (permit group 1, finiteness/positivity only, no formula recomputation): `PLAN_NOT_OK` when status != OK or stage != COMPLETE (then no other plan tag); otherwise `PLAN_INVALID_ID` when signal_id or setup_id is blank (same rule as the builder) and `PLAN_INVALID_VALUES` when any of e_out, s_out, tp, level_2r, partial_price, r_geom, volume_out, risk_model is not a finite number > 0. Direction and labels are not relied on and not checked. A zero/uninitialized plan or a NaN risk_model can never be ALLOWED.

## 3. Pending cancel decision - `TP_CancelDecision` / `cancel_decision`
Inputs: pending_exists, its signal_id, position_exists, explicit events as a bitmask DIRECTION_CHANGE 1, OPPOSITE_SIGNAL 2, SESSION_END 4, NEWS_BLOCK 8, DAILY_LIMIT 16. Checks in order: unknown bits or negative mask -> `INVALID_INPUT` (`INVALID_EVENTS`, even without a pending); no pending -> `NO_PENDING` (an open position alone gives no request); pending with a blank id -> `INVALID_INPUT` (`INVALID_PENDING_SIGNAL_ID`); mask 0 -> `NO_EVENT`; else `CANCEL_REQUEST` with reasons in the order above (no semantic effect: all lead to the same request). `positions_untouched` is always true (exhaustively tested over all masks and flags); `cancel_pending` is only the request for the PENDING order, label `CANCEL_REQUEST_ONLY / NOT_SENT`. No expiry by time/candles, no cooldown, no re-entry, nothing is sent.

## What this task does NOT decide (open policies)
The base of the 1%, costs, combined 2% numbers, 2 vs 3 trades per day, what counts as a win/loss, pending-order risk reservation, manual-trade ownership (netting/hedging), where data readiness/session/news/spread come from and their thresholds, time zone/DST handling, broker order check and placement, partial 80/20 volume split and the remainder when TP == 2R, expiry/cooldown/re-entry, restart recovery and persistence of the registry, EA wiring, the choice of FVG/structure/target and T002/T003 priority.

## Conventions needing review
1. Strictly `<` for positions and trades, `<=` for the combined risk (inclusive cap).
2. The 4-ulp risk tolerance (a real cent above the cap blocks).
3. `DATA_UNRELIABLE` as a separate tag when the state is READY but the flag is false; the flag is ignored when the state is NOT_READY/UNKNOWN.
4. Counts must be integers >= 0 and money values finite >= 0; an unknown count is passed as an invalid value and blocks.
5. All reasons are listed in a fixed order (permit); the registry check precedes the limit checks.
6. Limits of 0 are accepted as values (they block everything).
